## TP-001-GetProductStatus-Plan
### Назначение:
Объектом тестирования является REST API, реализованный методом GET по следующему шаблону: /products/{productId}/status?authToken=&recalculate=&owner=&region=. Интерфейс позволяет получать статус продукта по его уникальному идентификатору, а также дополнительно принимать ряд параметров (authToken, recalculate, owner, region).
### Область тестирования
Функциональные области, которые подлежат тестированию:
- Получение статуса продукта по идентификатору (productId).
- Обработка корректных и некорректных параметров (recalculate, owner, region).
- Авторизация через параметр authToken.
- Проверка работы API при различных состояниях продукта (готовый/не готовый).
- Контроль HTTP-кодов и содержимого ответов в ситуациях ошибки.
### Входные параметры:
- productId — идентификатор продукта (строго обязателен)
- authToken — токен авторизации и аутентификации (числа и буквы длиной 16 символов)
- recalculate — булевый параметр (true/false/null) (необязательный)
- owner — владелец продукта (текстовое значение) (необязательный)
- region — регион продукта (текстовое значение) (необязательный)
### Требования:
- Код ответа 200 при успешном получении статуса продукта
- Значение статуса продукта 0/1 (не готов/готов)
- Код ответа 404 при отсутствии продукта
- Код ответа 401 при неверном или отсутствующем токене
- Код ответа 500 при внутренней ошибке сервера
### Виды тестирования и стратегия:
- Функциональное тестирование: Проверка работы API при нормальном функционировании, корректных и некорректных данных.
- Негативное тестирование: Тестирование с целью выявления реакции API на неверные данные, непредусмотренные случаи и аномалии.
- Граничное тестирование: Проверка поведения API при предельных значениях параметров.
- Регрессионное тестирование: Периодическое повторение тестов после внесённых изменений, чтобы исключить появление регрессий.
- Попарное тестирование: Проведение тестов с разными комбинациями параметров для поиска скрытых багов.
### Критерии начала тестирования:
- Завершенность разработки необходимого функционала.
- Готовность тестовой платформы (стенда).
- Наличие документации API и руководства по тестированию.
- Утверждение тест-кейсов ответственными лицами.
### Критерии завершения тестирования:
Тестирование считается завершённым, если:
- Все тест-кейсы проведены и их результаты зафиксированы.
- Выявлено минимальное число критических дефектов (Blocker/Critical).
- API стабильно и предсказуемо возвращает корректные ответы в рамках требований.
